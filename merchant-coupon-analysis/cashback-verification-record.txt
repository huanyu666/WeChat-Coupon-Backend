Web cashback query verification (redacted)
==========================================

Endpoint
--------
  POST /act/ge/queryPoiByRecallBiz
  recallBizId=cpsPromotionOrderMulti
  csecversion=4.3.0

Positive first-merchant case
----------------------------
  command: node web-cashback-query.js <MATCHING_CASHBACK_PAGE_URL>
  exit: 0
  literal result: HTTP 200; ret=0; decision=HAS_CASHBACK
  literal values: orderRatePercent=20; orderMaxYuan=22.5;
                  reviewRatePercent=5; reviewMaxYuan=1.5;
                  totalMaxYuan=24; userSignStatus=CAN_SIGN;
                  validInventory=3; totalInventory=5

No-match case
-------------
  command: node web-cashback-query.js <NONMATCHING_CASHBACK_PAGE_URL>
  exit: 0
  literal result: HTTP 200; ret=0; decision=NO_CASHBACK;
                  reason=FIRST_POI_MISMATCH

Controls
--------
  A target found in infos[1] did not move to infos[0] when supplied as
  mediumParams.poi_id_str. The array ordering is authoritative for this
  delivery, and later merchants are ignored.

  The same request succeeded without Cookie, Authorization, Origin or
  Referer. A fresh mtgsig generated by web-h5sign.js was required.

Logged-page comparison
----------------------
  The logged-in page used the same endpoint and displayed the target merchant
  with recallBizId=cpsPromotionOrderMulti. Replaying the old
  cpsSelfPromotionOrder value returned a different first merchant; replaying
  cpsPromotionOrderMulti returned the target as infos[0]. This isolates the
  earlier discrepancy to the recall value, not HTTP reuse. Login-only calls
  (getUserInfo and mission/cash/back) add user state and quota context; they
  are not required for anonymous list replay.

Field units
-----------
  Current page JavaScript renders userMaxRatio / 100 as percent and
  userMaxCommission / 100 as yuan. The review fields use the same divisors.
  The page labels these values as maximum cashback, not guaranteed fixed cash.
