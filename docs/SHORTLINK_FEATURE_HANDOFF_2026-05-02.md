# 短链功能交接说明

## 当前情况

- 小程序链接解析问题已经修到“能回复”。
- 根因分两层：
  1. `zmkey` 读取路径之前不对，已修复。
  2. 小程序处理器生成的回复里长链接过多，微信被动回复会被静默吞掉。
- 目前生产为了保证可见性，已经把小程序回复压成更保守的短内容版本。

## 为什么要做短链

- 这个项目里很多回复链接都是超长 URL，尤其是美团 H5 链接。
- 微信被动回复对内容长度、XML 体积、链接形态都比较敏感。
- 商家链接场景还能勉强撑住，小程序解析场景更容易超限。
- 所以短链不是优化项，基本属于回复稳定性的基础设施。

## 需要优先转成短链的内容

优先级从高到低：

1. 小程序解析处理器里的主商家券链接
2. 小程序解析处理器里的第二条变体链接
3. 返现活动链接
4. `extra_params_url`
5. 大众点评 / 红包 / 其他补充跳转链接
6. 其他文本处理器里所有发给用户的长 H5 链接

原则：凡是要进入公众号被动回复的外链，默认都应该先过短链。

## 已知现象

- 之前日志已经看到小程序回复成功生成，但被微信吞掉。
- 压短后可以收到回复，说明问题确实和回复内容形态有关。
- 生产里还出现过 `/j/...` 返回 `404`，说明现有短链链路还不稳定，不能直接依赖。

## 下一轮实现建议

1. 在本机服务内实现完整短链能力，不依赖外部平台。
2. 提供稳定的短链路由，例如 `/j/{code}`。
3. 提供短链存储、创建、解析、过期/冲突处理。
4. 在“生成回复内容”之前统一把外链转成短链。
5. 先接入小程序处理器，再逐步推广到其他处理器。
6. 增加日志：原始 URL 长度、短链 code、最终回复 `content_bytes/xml_bytes`。

## 验收标准

- 小程序链接回复恢复为较完整内容后，用户仍能稳定收到。
- 生产日志里不再出现短链 `404`。
- 公众号被动回复里的外链大部分都变成本站短链。
