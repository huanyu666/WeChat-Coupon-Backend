# 排行榜三方数据源本地分析交接文档

## 目的

为后续重做本站排行榜，完成三个外部数据来源的协议分析与可实现性确认。

在新排行榜完整上线前，当前生产逻辑必须保持不变：公众号和 Web 用户继续通过本站短链跳转到现有第三方排行榜，不切换到本站自建排行榜，也不改变现有查单流程。

本文件用于把浏览器侧分析交给本地具备可视化浏览器的 AI。完成后，请把“交付结果”部分要求的内容交回主站项目，由主站侧实现正式采集、存储、定时和展示能力。

## 目标设计边界

计划中的新排行榜有三个数据来源：

1. `https://naiba666.com/md/index.html`
2. `https://mt.liliabc.fun/page/wm/md?key=mt-time-07291200&t=1785211206&name=%E9%BA%A6%E5%BD%93%E5%8A%B3`
3. `https://waimaiyouhui.top/order-rankings?keyword=%E9%BA%A6%E5%BD%93%E5%8A%B3&date=2026-07-29&slot_time=12%3A00`

预期业务口径：

- 商家名称、排序及主要接单时间优先使用来源 1。
- 来源 2、3 用于补充、比对或后续容错，具体优先级待分析结果确认后再定。
- 到达指定场次时间后，主站在可配置的持续时间内按固定间隔轮询上述来源；时间窗口结束即停止抓取。
- 不在本次分析阶段修改生产代码、第三方跳转、短链或排行榜数据库。

## 安全要求

- 不要在交付文档、截图、HAR 或 cURL 中暴露可用账号密码、Cookie、Authorization、token、个人订单号或完整手机号。
- 账号密码仅可用于本地浏览器登录来源 1，不要发送给主站或写入项目代码。
- 若请求带 Cookie，请保留 Cookie 字段“是否必需”的结论，但将具体 Cookie 值替换成 `***`。
- 若接口需要签名、动态 nonce、时间戳、验证码或浏览器指纹，必须明确说明，不能凭猜测省略。
- 不要对任何来源进行高频压测。分析时每个动作执行 1 到 3 次即可。

## 通用分析步骤

在 Chromium/Chrome 中按以下方式操作每一个来源：

1. 打开开发者工具，进入 `Network`。
2. 勾选 `Preserve log` 与 `Disable cache`。
3. 过滤 `Fetch/XHR`；若没有请求，再观察 `Doc`、`JS`、`Other`。
4. 清空请求列表后刷新页面一次。
5. 依次完成“切换时间”“切换商家或关键词”“翻页/加载更多”（若页面支持）。
6. 对每个影响榜单数据的请求记录：请求 URL、方法、Query 参数、请求体字段、必要请求头、状态码、响应 JSON 或 HTML 的结构摘要。
7. 对关键请求右键选择 `Copy` -> `Copy as cURL`，然后脱敏敏感值。
8. 保存一个最小 HAR 文件或响应样例。HAR 也必须先移除 Cookie、Authorization、账号密码等敏感字段。
9. 记录浏览器时区、页面显示时区，以及请求中时间参数的单位（秒、毫秒、日期字符串）。

## 本地 Codex 与人工登录协作步骤

本地 Codex 应实际执行本文件的分析工作，不需要人工代为抓包。唯一例外是需要人工完成的登录、验证码、扫码或其他交互认证。

执行规则：

1. Codex 先打开目标页面并开始 Network 记录。
2. 若出现登录页、验证码、扫码、二次验证、账户选择或浏览器安全提示，Codex 必须立刻停止后续网络操作，并明确提示：

   ```text
   检测到需要人工登录。请你在当前浏览器窗口完成登录；完成后回复“已登录”，我将从当前会话继续抓取排行榜数据请求。
   ```

3. 人工在同一浏览器 profile/window 中完成登录后，只回复“已登录”。不要把账号密码、Cookie 或二维码内容发送到聊天记录。
4. Codex 收到“已登录”后，先确认当前页面已进入榜单页，再清空 Network 记录，重新执行刷新、切换时间、切换商家、分页等分析动作。
5. Codex 不得尝试读取、导出、打印、持久化或提交浏览器 Cookie、密码、认证 token、二维码原文和 Authorization 值。
6. 若登录后请求不再带 Cookie，Codex 应记录“未观察到 Cookie 依赖”；若请求仍带 Cookie，则只记录“Cookie 存在且可能必需”，并在交付的 cURL/HAR 中将值替换为 `***`。
7. 如果人工登录后仍无法进入、请求被拦截或页面提示频率限制，Codex 应记录页面提示、状态码和脱敏响应摘要，不反复重试或规避限制。

可直接交给本地 Codex 的任务说明：

```text
请阅读 docs/排行榜三方数据源本地分析交接文档.md，并按文档完整分析三个排行榜数据来源。

你可以自行使用浏览器和开发者工具抓取网络请求。遇到需要登录、验证码、扫码或任何人工认证时，立即暂停，明确要求我在当前浏览器完成操作；不要索取或输出账号密码、Cookie、token 或二维码内容。等我回复“已登录”后，继续使用同一浏览器会话完成分析。

分析完成后，在 rankings-analysis/analysis.md 输出交付文档，并按原文档要求保存脱敏后的 cURL、响应样例和必要的 HTML/HAR。不得修改现有项目排行榜生产代码、短链跳转或配置。
```

## 来源 1：naiba666.com

### 已知情况

- 页面地址：`https://naiba666.com/md/index.html`
- 本地可能需要先登录。
- 已知本地测试结论是：登录完成后，后续榜单数据请求可能不需要 Cookie。
- 主站服务器当前无法稳定完成该站 HTTPS 连接，不能据此推断接口不存在或不需要认证。因此本地浏览器抓包是本来源的唯一可靠分析依据。

### 需要确认

1. 登录请求：
   - 登录地址、方法、表单字段名。
   - 登录成功是否写入 Cookie/localStorage/sessionStorage。
   - 榜单数据请求是否实际携带或依赖这些状态。
2. 榜单请求：
   - 是服务端渲染、XHR/fetch、WebSocket、SSE，还是其他方式。
   - 商家列表请求与单商家时间列表请求是否分开。
   - 选择日期、场次、时间、商家后，各参数如何传递。
   - 是否有分页、游标、最大返回量和排序字段。
3. 响应语义：
   - 商家名称、唯一标识、排名、接单时间、记录时间、订单数量等字段。
   - 时间字段的格式、时区与精度。
   - 空数据、未开始、已结束、请求过频、未登录时的响应。
4. 稳定性：
   - 是否有请求频率限制或防爬提示。
   - 刷新/重复请求时是否返回相同数据或触发错误。

### 建议操作

1. 在本地登录后，先记录登录前后 Cookie/localStorage 的差异，但不要导出真实值。
2. 清空 Network，刷新榜单页，记录所有数据请求。
3. 切换至少两个不同的场次或时间。
4. 选择至少两个不同商家或关键词。
5. 若有刷新按钮、加载更多或分页，分别操作一次。
6. 退出登录或无痕窗口重复一次“加载榜单”的请求，用于验证 Cookie 是否真不需要。

## 来源 2：mt.liliabc.fun

### 已确认的初步结论

- 示例页面可直接被主站获取，当前未观察到二次 XHR/fetch 请求。
- 数据由页面服务端直接写入 HTML 内嵌 JavaScript，形式类似：

```javascript
var shopData = {
  "商家名": [1785297601, 1785297602]
};
var myTime = 1785211206;
```

- `shopData` 的键是商家名，数组元素看起来是秒级 Unix 时间戳。
- URL 参数已观察到：
  - `key=mt-time-MMDDHHmm`
  - `t=<秒级 Unix 时间戳>`
  - `name=<商家名>`
- 页面本身可切换场次，前端将选择值拼成 `mt-time-MMDDHHmm` 后重新加载页面。

### 仍需本地确认

1. `key` 是否总使用北京时间的 `MMDDHHmm`，是否允许非整点/非半点场次。
2. `t` 的含义：用户接单时间、查询时间还是个人定位时间；单位是否始终为秒。
3. `name` 是否必须完全匹配，是否 URL 编码，商家名不一致时的回退规则是什么。
4. 是否存在未在静态页面中出现的请求、反爬校验、重定向或响应头限制。
5. 空数据、错误时间、未来场次、错误商家名时的 HTML 结构。
6. 同一个 `key` 下，多次刷新是否数据增量变化；需要记录一次完整页面样例和一次稍后刷新后的差异。

### 建议抓取样例

- 用一个已有数据的商家和场次加载一次。
- 把场次切换为相邻的前后各一个场次，再各记录一次 URL 与 HTML 中 `shopData` / `myTime`。
- 使用一个明显不存在的商家名，记录返回页面。
- 如页面允许，记录 URL 改变的全过程。

## 来源 3：waimaiyouhui.top

### 已确认的初步结论

页面本身通过 JSON 接口加载数据：

```text
GET https://waimaiyouhui.top/api/order-rankings/query
```

已观察到的查询参数：

- `keyword`：商家关键词。
- `date`：日期，形如 `2026-07-29`。
- `slot_time`：场次时间，形如 `12:00`。
- `page_size`：页面默认值为 `50`。
- `cursor`：存在下一页时使用。
- `rank_token`：仅用于个人排名定位；新排行榜的数据采集不应依赖或使用个人定位 token。

接口页面逻辑预期响应包含：

- `ok`
- `rankings`
- `total`
- `has_more`
- `next_cursor`
- 可能还有 `user_rank`、规则或关键词元数据。

### 仍需本地确认

1. 完整 JSON 样例，尤其是每条 `rankings` 的字段：商家、接单时间、排名、日期、场次、唯一订单标识是否存在。
2. `keyword` 是精确匹配、包含匹配还是规则关键词。
3. `date`、`slot_time` 的时区和可选范围。
4. `page_size` 上限，`cursor` 的格式及分页是否稳定。
5. 空数据、过期日期、未来时间、非法 cursor 的响应。
6. 是否无需 Cookie/Authorization；在无痕窗口验证一次即可。

### 建议抓取样例

1. 用示例 URL 记录首个 API JSON 响应。
2. 选择一个有超过 50 条记录的场次，触发“加载更多”，记录带 `cursor` 的请求和响应。
3. 将关键词改成不存在值，记录空结果。
4. 将日期或场次改为相邻值，确认参数变化与返回数据关系。

## 时间与轮询重点

后续实现最容易出错的是时间口径。每一个来源都必须给出以下结论：

| 项目 | 来源 1 | 来源 2 | 来源 3 |
| --- | --- | --- | --- |
| 页面显示时区 | 待填 | 待填 | 待填 |
| 请求时间格式 | 待填 | 初步为 `mt-time-MMDDHHmm` | 初步为 `date + slot_time` |
| Unix 时间单位 | 待填 | 初步为秒 | 待填 |
| 数据开始出现时间 | 待填 | 待填 | 待填 |
| 数据稳定/停止增长时间 | 待填 | 待填 | 待填 |
| 推荐轮询间隔 | 待填 | 待填 | 待填 |
| 推荐轮询总时长 | 待填 | 待填 | 待填 |
| 限流或错误特征 | 待填 | 待填 | 待填 |

不要根据单次请求推断轮询频率。建议在一个真实场次开始后，以人工低频观察方式记录：开始时、开始后 1 分钟、3 分钟、5 分钟、10 分钟的数据条数和最后时间，以确定后续安全的采集窗口。
